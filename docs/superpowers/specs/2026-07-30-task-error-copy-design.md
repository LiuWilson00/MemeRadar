# 任務錯誤訊息：使用者文案 / 技術細節分離

2026-07-30。起因：梗圖大戰失敗時，使用者看到的是
`推薦失敗：NVIDIA VLM 所有 key 皆不可用且已達等待上限 8s（最後錯誤：Request timed out.）`
——供應商名稱、內部術語、秒數全都露在前台。

## 決策

**`error` 是產品文案，`error_detail` 是技術細節。**

| 欄位 | 內容 | 誰看 |
|---|---|---|
| `tasks.error` | 梗圖魂調性的一句話 | 使用者（前台 `api.ts` 原封不動顯示） |
| `tasks.error_detail` | `例外型別: 原始訊息`（截斷 2000 字） | 我們 debug |

兩欄都在 `GET /tasks/{id}` 的 JSON 裡回。

### 為什麼 detail 公開

`/tasks/{id}` 是公開端點，所以 `error_detail` 對任何拿到 task_id 的人可見。
評估過三個做法：公開（選這個）、只給 admin、寫進 `client_errors` 表。
選公開是因為「curl 一下就看得到真因」這件事的價值高於風險——task_id 是隨機 32 hex、
且與 client_id 綁定，實務上外人拿不到。**若日後要收緊，把 `error_detail` 改成僅
admin 認證下回傳即可，前台不受影響（它只讀 `error`）。**

### 為什麼依例外型別分派

`memeradar/api/error_copy.py` 用 `isinstance` 對照，不比對錯誤訊息字串——
比對字串的話，哪天有人改了某句錯誤訊息，文案對應會**悄悄**失效並掉回 fallback。

為此把 embedding 全掛時拋的裸 `RuntimeError` 改成專用的 `EmbeddingUnavailableError`。

## 文案（梗圖魂）

| 情境 | 文案 |
|---|---|
| VLM 掛掉 / 逾時（含模型下架） | 腦袋轉到冒煙了，再給我一次機會好嗎。 |
| embedding 供應商全掛 | 這題我真的想不出梗，讓我先自閉一下。 |
| 意圖分析被安全政策拒答 | 這個話題我不敢接，換一句試試？ |
| 對方梗圖被拒絕解讀 | 這張圖我不敢解讀，換一張試試？ |
| 截圖解析失敗 | 這張截圖我瞳孔地震，換一張清楚點的？ |
| 其他 / 未知 | 出事了阿 Sir，但我不知道出什麼事。 |

`tests/test_error_copy.py` 有一支守門測試，逐字檢查每句文案不含
`nvidia`/`模型`/`HTTP`/`逾時`/`供應商`/狀態碼等內部字眼——新增文案時它會擋下洩漏。

## 範圍

只動任務失敗這條路。`/recommend` 的 503「推薦服務忙碌中」等 HTTP 層錯誤不在此次範圍。
舊資料的 `error` 欄仍是技術訊息，不回填（歷史任務不會再被使用者看到）。
